# Анализ проблем архитектуры InsureTech

## Проблема 1: Синхронные запросы к страховым компаниям

| Аспект | Описание |
|--------|----------|
| **Описание** | `ins-product-aggregator` при каждом запросе синхронно опрашивает все страховые компании (сейчас 5, скоро будет 10+) и агрегирует результаты. |
| **Риски** | • Время ответа растет линейно с количеством компаний (O(n)) <br>• Отказ одной компании замедляет/блокирует весь запрос <br>• Таймауты вызывают ошибки в `core-app` и `ins-comp-settlement` <br>• При 10+ компаниях время ответа может превысить допустимые лимиты |
| **Влияние на бизнес** | • Ухудшение пользовательского опыта (долгая загрузка страниц) <br>• Сбои в формировании реестра страховок |

## Проблема 2: Устаревшие локальные копии данных

| Аспект | Описание |
|--------|----------|
| **Описание** | `core-app` (обновление раз в 15 минут) и `ins-comp-settlement` (раз в сутки) хранят локальные копии данных о продуктах и тарифах. |
| **Риски** | • Клиенты видят устаревшие тарифы (до 15 минут) <br>• Оформление страховки может идти по неактуальным условиям <br>• Расхождения в данных между сервисами (разная периодичность обновления) |
| **Влияние на бизнес** | • Клиенты могут оформить страховку по тарифу, который уже изменился <br>• Дополнительные затраты на урегулирование спорных ситуаций |

## Проблема 3: Синхронный запрос между core-app и ins-comp-settlement

| Аспект | Описание |
|--------|----------|
| **Описание** | `ins-comp-settlement` раз в сутки синхронно запрашивает у `core-app` все оформленные за день страховки через REST API. |
| **Риски** | • При росте количества страховок запрос может выполняться минуты <br>• Высокая нагрузка на `core-app` в ночное время <br>• При сбое `core-app` реестр не формируется |
| **Влияние на бизнес** | • Задержки в расчетах со страховыми компаниями <br>• Финансовые потери от несвоевременных выплат агентских премий |

## Проблема 4: Отсутствие единого источника правды

| Аспект | Описание |
|--------|----------|
| **Описание** | Данные о продуктах, тарифах и оформленных страховках дублируются в нескольких сервисах с разной периодичностью обновления. |
| **Риски** | • Несогласованность данных между сервисами <br>• Сложность отладки инцидентов <br>• Увеличение operational overhead при масштабировании |
| **Влияние на бизнес** | • Риск ошибок в расчетах агентских премий <br>• Сложность аудита и compliance |

## Проблема 5: Задержки и ошибки при взаимодействии со страховыми компаниями

| Аспект | Описание |
|--------|----------|
| **Описание** | API страховых компаний могут работать нестабильно, задерживать ответы или возвращать ошибки. |
| **Риски** | • Cascade failures (ошибка одной компании → ошибка во всем сервисе) <br>• Невозможность получить данные при временных сбоях <br>• Отсутствие механизма повторных попыток |
| **Влияние на бизнес** | • Снижение доступности сервиса <br>• Репутационные потери |

## Проблема 6: Планируемый рост нагрузки

| Аспект | Описание |
|--------|----------|
| **Описание** | InsureTech планирует подключить еще 5 страховых компаний (всего 10+) и ожидает рост пользователей после рекламной кампании. |
| **Риски** | • Синхронный подход не масштабируется (O(n) время ответа) <br>• Текущая периодичность обновления может не справляться с нагрузкой <br>• Увеличение числа интеграций требует более сложного управления |
| **Влияние на бизнес** | • Невозможность масштабирования бизнеса <br>• Потеря конкурентных преимуществ |
